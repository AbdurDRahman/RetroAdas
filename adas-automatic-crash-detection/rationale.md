## 1. The datasets

### 1.1 The most important idea: the chip carries no data

The ESP32 holds **no dataset**. It runs a fixed set of rules and eight
weights. Data was used **on the laptop, once**, for two jobs only:

- **Choosing numbers.** Data was used to pick the eight score weights and a
  few thresholds. This is "training" or "tuning".
- **Measuring.** Data was used to check how well those numbers work on
  recordings that were **not** used to choose them. This is "testing".

Keeping those two jobs on *separate* data is what makes the results
believable. If you tune and test on the same recordings you are grading
your own homework with the answer key. So for every dataset below, note
which of the two jobs it did.

### 1.2 Why public datasets at all

You cannot crash cars to test a crash detector. Feature 3's own spec
names this as an open problem ("What real-world data will you use to set
the abrupt-motion thresholds?"). The solution is to borrow other people's
recordings of real crashes and real driving. Three were needed, because
no single dataset has everything:

| need | dataset that has it |
|---|---|
| many **real crashes**, labelled by humans | VZCrash |
| hours of **ordinary driving** with road-type labels, rigid sensor like ours | PVS |
| very **rough roads**, potholes, loose mount (a stress test) | RoadSens-4M |

### 1.3 VZCrash

| | |
|---|---|
| Who | Verizon Connect research group. Paper: Bianconcini et al., *VZCrash: A Large-Scale IMU Dataset of Ego-Vehicle Crashes*, IEEE ITSC 2026, arXiv:2606.06074. |
| What | ~190,000 recordings, each **16 seconds**, from motion sensors built into dashcams of commercial fleet vehicles (cars, vans, trucks). Accelerometer (g) and gyroscope (°/s) at **100 Hz**, GPS speed at 1 Hz. |
| Labels | **crash / near-miss / normal driving.** Expert reviewers decided each label by watching the **dashcam video**, with three-way agreement. 31,090 recordings are verified crashes. |
| A detail you must know | **Every** recording, even "normal driving", was **triggered by the vehicle's harsh-driving detector**: hard braking, a shock, or a big jolt. So the non-crash recordings are not calm driving. They are the hardest possible "looks like a crash but isn't" cases: potholes, off-road, trailer coupling, near-misses. |
| Licence | CC BY-NC 4.0 (non-commercial). Allowed for a university project. Cite the paper. |
| Split | The authors split the data **by vehicle** into train / validation / test, so no vehicle appears in two splits. |

**How we used it:**

| part | size | job | used by |
|---|---|---|---|
| **train**, files 0 and 1 | 25,084 recordings (**286 crashes**) | **choosing** the 8 score weights and the score threshold | `eval/fit_model.py` |
| **test**, files 0 and 1 | **24,174** recordings: 4,221 crashes, 3,633 near-misses, 16,320 normal | **measuring** recall and false-positive rate. Never used to choose a weight or the score threshold. | `eval/run_eval.py`, `eval/compare_v1.py` |

*Why VZCrash:* it is the only large public dataset of **real, verified
vehicle crashes** recorded by an IMU at 100 Hz. It is also the dataset
the previous engineer benchmarked on, so v1 and v2 can be compared
directly.

*Its limits:* the IMUs are fleet dashcam units, not an MPU-6050. They
have the same class of sensor and range, but a different model and
mounting. The recordings are only 16 s long and harsh-triggered, so it
cannot tell you "false alarms per hour of normal driving" directly
(section 1.6). It contains essentially no labelled rollovers.

### 1.4 PVS — Passive Vehicular Sensors

| | |
|---|---|
| Who | Menegazzo & von Wangenheim, Federal University of Santa Catarina (Brazil). Published on Kaggle and the UFSC file server. |
| What | **Nine drives, 3.0 hours**, three different cars and drivers, three routes. An **MPU-9250** (the MPU-6050's 9-axis sibling) is **rigidly mounted on the dashboard**, 100 Hz, ±8 g, plus GPS. |
| Labels | Every sample is labelled with surface (asphalt / cobblestone / dirt), roughness (good / regular / bad) and speed bumps. Individual potholes are **not** labelled. |
| Licence | CC BY-NC-ND 4.0. |

**How we used it:**

1. **Measuring false alarms per hour of real driving.** Any CRASH or
   ROLLOVER alarm in PVS is false by definition, because nobody crashed.
   This is the main real-road number.
2. **Tuning the pothole branch.** `eval/sweep_road.py` tried 72
   combinations of the pothole thresholds against PVS's labelled speed
   bumps (section 2.6).
3. **Extra "not a crash" examples for the score.** The 1,295 violent
   moments in PVS (bumps, cobblestone) were added to the training
   negatives so the score learns what rough roads look like.

Uses 2 and 3 mean PVS is not fully independent of the design, so we
checked that the main result doesn't depend on it: the score was **refit
with PVS left out entirely**, and PVS still produced **0** crash alarms
(section 3.3).

*Why PVS:* it is the only public dataset we found with **hours of
continuous driving**, a **rigidly mounted sensor of the same family** as
ours, and **road labels** that include rough surfaces and speed bumps.
Those are exactly the things that cause false alarms.

### 1.5 RoadSens-4M

| | |
|---|---|
| Who | Khandakar et al., 2025 (Qatar University and partners). Figshare, doi:10.6084/m9.figshare.30341143. |
| What | 101 phone recordings, **1.7 hours**, urban roads in Bangladesh, using the Sensor Logger app at 100 Hz. The phone sat on the dashboard. |
| Labels | An observer pressed a button over "pothole" and "bump" **stretches** of road. |
| Licence | CC BY 4.0. |

**How we used it:** a second false-alarm test on very rough roads with a
**loosely mounted** phone, which is worse than our rigid box. It was also
part of the training negatives (42 moments).

*Its limit, stated openly:* the labels mark long stretches, not
individual holes, and the phone signal contains almost no clear
"drop-then-hit" pothole signatures. So it **cannot** measure pothole
recall. We report it as a stress test only. `own_data.md` describes the
recording that would measure pothole recall properly.

### 1.6 Turning "percent of events" into "alarms per hour"

Your target was framed **per hour**. VZCrash gives a rate **per harsh
event**: 2.5 % of non-crash harsh events set off the alarm. To convert,
we need to know how many harsh events a vehicle produces per hour, and
the VZCrash paper reports exactly that for a real fleet: **735,000 harsh
events from 123,000 vehicles in 48 hours**, which is about 6 per vehicle
in 48 h.

Assuming 8 hours of driving a day, that is 0.37 harsh events per driving
hour. 2.5 % of 0.37 is **0.009 false alarms per driving hour**, or about
**one per 100 driving hours**. Counting wall-clock hours instead gives
about one per 300 hours. This is conservative, because commercial fleet
vehicles are driven harder than private cars.

The direct measurement is PVS: **0 false alarms in 3.0 hours**. With zero
events observed in 3 hours, the 95 % upper confidence limit on the rate is
3 / 3.0 h = **1 per hour** (the statistician's *rule of three*). Both
figures meet the "≤ 1 per hour" target.

## 2. How the logic was decided

This is the decision trail: what was known at each step, what was
chosen, and why. A panel will want to hear that the design came from
evidence, not from guesses.

### 2.1 Start: what v1 had already proven

The first engineer benchmarked simple rules on VZCrash (`results.md`).
Four of their findings shaped everything that followed:

1. Textbook g-force bands (5 / 20 / 40 g) are useless on car IMUs. No
   real crash in the data exceeds 7.3 g, and the typical crash peaks
   near 4 g.
2. Peak g alone tops out around 60–65 % recall at a low false-positive
   rate.
3. A weighted combination of g and tilt beats g alone (their "Test 3b").
4. GPS speed drop cannot tell a crash from a near-miss, because 99 % of
   near-misses also slow down sharply.

### 2.2 The physical insight (tyre friction)

Step back from the numbers and ask why braking and crashes look alike.
Both are horizontal deceleration. The difference is **how much and for
how long**. A car brakes only through its tyres, and dry asphalt limits
that to about **1.0–1.2 g**. A crash pushes the body directly, so it
easily exceeds this for tens of milliseconds. Potholes and bumps are
different again: mostly **vertical**, with no net change in speed.

**Decision:** split every reading into **vertical** and **horizontal**
parts, and measure the horizontal acceleration **sustained over 50 ms**
rather than the single-sample peak. Fifty milliseconds is 5 samples. That
is long enough to reject one-sample spikes and short enough to catch a
crash pulse, which lasts 30–150 ms.

### 2.3 Hard rules where physics is certain

If sustained horizontal acceleration is more than **twice the tyre
limit**, nothing but a collision can explain it. **Decision:** override 1
is **sustained horizontal ≥ 2.5 g → crash, always**. It has no fitted
parameters and doesn't depend on any dataset being representative. Its
check on real roads: the strongest sustained-horizontal value in 4.7 h of
real driving was **1.45 g**, well short of 2.5.

Some severe crashes have a large *vertical* component: kerbs, ditches, a
car riding under a truck. Their horizontal part can sit at 1.3–2.2 g with
a 4–5 g peak. **Decision:** override 2 is **peak ≥ 4 g AND sustained
horizontal ≥ 1.2 g → crash, always**. The 1.2 g is the tyre limit again;
the 4 g is the boundary of the "severe" tier.

*Disclosure:* override 2 was added after seeing that 7 of the 2,555
severe test crashes were missed without it. Looking at the test data
before adding a rule is a form of test leakage, so it was **re-checked on
the training split**. There, 150 severe crashes exist, the other rules
missed 2, override 2 caught 1, and it added only 7 false triggers out of
24,776 negatives (0.03 %). The rule is supported by independent data, and
its two numbers are physical boundaries, not values tuned to make the
test look good.

### 2.4 A fitted score for the grey zone

Between "obviously braking" (under ~1.2 g horizontal) and "obviously a
crash" (over 2.5 g) lies a grey zone. A hand-made threshold in that zone
is guesswork. **Decision:** describe each violent moment with eight
measurements and let a **logistic regression** learn how to weigh them.
This is the simplest statistical classifier there is: a weighted sum and
a cut-off line.

| measurement | why it was included |
|---|---|
| peak total g | v1's best single rule |
| sustained horizontal g (50 ms) | the tyre-limit quantity |
| ΔV over 100 ms and over 300 ms | velocity change, the quantity airbag controllers use (crash pulses stop changing within ~100 ms; braking keeps going) |
| vertical ÷ horizontal | separates pothole-shaped events from crash-shaped events |
| peak pitch/roll rate | rotation after an impact (Pranoto et al.: bumps rotate, braking does not) |
| tilt jump (filter α = 0.90) | v1's Test 3b showed it adds 12–17 points of recall |
| peak vertical g | lets the score tell a hard pothole from a crash |

*Why logistic regression and not a neural network:*

- **It runs on an ESP32.** Eight multiply-adds per event.
- **It can be inspected.** The learned weights can be read and checked
  against the physics. Sustained horizontal g gets the largest positive
  weight (+3.61); the vertical-ratio gets the largest negative weight
  (−2.25). The model learned the tyre-limit idea by itself.
- **It needs little data.** It was fitted on 286 crashes and generalised
  to 4,221 unseen ones.
- **The guarantees don't depend on it.** The severe tier is caught by the
  overrides, whatever the score does.
- **The precedent supports it.** The Chalmers smartphone study found a
  plain threshold gives about 10 false alarms per hour while a simple
  classifier is "vastly better". We use the simplest classifier that
  achieves that.

*How the threshold was chosen:* on a quarter of the **training** data
held back from fitting, as the lowest cut-off that still catches ≥ 95 %
of moderate-and-above crashes. That gives **2.37**. The test split had no
say in it.

### 2.5 Rollover

The v1 tilt filter was kept unchanged. The threshold is **60° held for
one full second**. The two source papers suggest 46° (Ibrahim 2016) and
70–80° (Chikaka 2021). v1's benchmark showed 46° fires in normal driving,
while 60° with the slow filter (α = 0.99) has a 0.3 % false rate. The
one-second hold rejects the brief fake tilt that a crash impact produces
in the filter.

### 2.6 Potholes

From the pothole literature (Mednis et al. 2011, four classic
algorithms): a wheel dropping into a hole produces a brief **near
free-fall** (G-ZERO), and hitting the far edge produces a **spike**
(Z-THRESH). A speed bump does the opposite: **lift, then drop**.

**Decision:** report a pothole when, on the vertical signal, a drop to
≤ −0.35 g is followed within 250 ms by a hit of ≥ +0.40 g, the whole event
lasts ≤ 400 ms, and the road was quiet for the half-second before (which
excludes cobblestone).

The numbers were chosen by sweeping **72 combinations** on PVS
(`eval/sweep_road.py`):

| setting | effect found in the sweep |
|---|---|
| trigger 0.30 g (vs Mednis's 0.40 g for phones) | sees 92–94 % of labelled speed bumps, vs ~50 % at 0.45 g |
| quiet-before gate, std < 0.15 g | the single largest reduction in false reports |
| hit ≥ 0.40 g | middle ground: 0.30 g gives ~2.5 reports/h on asphalt labelled "ok"; 0.45 g gives 0.4/h but bump sensitivity drops to 69 % |

Potholes never sound the alarm. They are sent to the Jetson as a hazard
for Feature 2.

### 2.7 Everything else

These came from the feature spec and from the previous engineer's
"known problems" list (`handover.md` §4):

- **Sanity clamp.** v1 had none, and the data contains 50 g glitches.
- **15 s cancel countdown.** The feature spec asks for 10–15 s.
- **GPS speed attached to reports but never used to decide.** This was
  v1's finding: speed drop doesn't separate crashes from near-misses.
- **100 Hz instead of 52 Hz.** Every dataset is 100 Hz, so thresholds
  transfer with no conversion.
- **Plain C, single-precision float, no dynamic memory.** These are the
  ESP32 rules v1 already set.

## 3. Why the result is good

### 3.1 The headline numbers

All are measured on data that was not used to choose them:

| what | result | target |
|---|---|---|
| Severe crashes detected (≥ 4 g peak or ≥ 2.5 g sustained horizontal; 2,555 crashes) | **100.0 %** | 100 % |
| Moderate crashes (3–4 g; 769) | 79.3 % | report honestly |
| Minor crashes (1.8–3 g; 817) | 31.8 % | report honestly |
| All 4,221 labelled crashes | 81.1 % | — |
| False alarms, 3.0 h real driving in three cars (PVS) | **0** | ≤ 1 per hour |
| False alarms, 1.7 h rough roads with a loose phone (RoadSens) | 0 | — |
| False-positive rate on harsh events (VZCrash) | 2.5 % ≈ 1 per 100–300 driving hours | ≤ 1 per hour |
| Compute per reading | ~50–150 ns on a laptop (varies with load); < 0.5 % of the ESP32 at 300× slower | fits easily |

### 3.2 Why "not 100 % of all crashes" is the correct answer

About one crash in five in VZCrash never produces more acceleration than
hard braking does: parking-speed contacts and bumper taps. For those, the
sensor signal is **physically the same** as an emergency stop. No
algorithm using only a body-mounted motion sensor can separate them. A
system that claimed to would also be calling emergency services for
every emergency stop.

Industry handles this the same way: every production system targets
**severe** crashes and says so in writing (section 4). The tiered target
was agreed for this reason, and it is the defensible position.

### 3.3 Why the numbers can be trusted

- **Train / test separation.** Weights and the score threshold come from
  VZCrash train files; recall and FPR are measured on test files. The
  dataset authors split by vehicle.
- **The real-road result survives leaving the data out.** Refitting the
  score **without any PVS data**:

  | model | test recall | test FPR | PVS crash alarms | RoadSens alarms |
  |---|---|---|---|---|
  | shipped (fitted with PVS + RoadSens negatives) | 81.1 % | 2.50 % | 0 | 0 |
  | refit **without PVS** | 82.3 % | 2.65 % | **0** | 0 |
  | refit on VZCrash train only | 81.9 % | 2.63 % | **0** | 0 |

  So the 0 on PVS is not an artefact of having trained on PVS.
- **The test-informed rule was re-checked.** Override 2 was confirmed on
  the training split (section 2.3).
- **The v1 reproduction matches v1's own published numbers.** Running
  v1's rules through our new harness gives exactly the figures in v1's
  `results.md`: 78.7 % at 3 G, 28.0 % at 5 G, 75.2 % for Test 3b at
  2 % FPR. The measurement pipeline therefore agrees with an independent
  earlier one.
- **What is measured is what runs.** The laptop harness loads the same
  compiled C file that the firmware compiles. The report also recomputes
  every decision offline and confirms it matches.

### 3.4 Honest limits — say these before you are asked

1. **The firmware has not run on a real board yet.** The detection code
   is the same file, but the MPU-6050 driver, timing and wiring are
   untested.
2. **Pothole recall is not measured.** No public dataset labels
   individual holes. The road branch is shown to react to 82 % of
   labelled speed bumps and to misreport none of them as potholes. A
   30-minute recorded drive (`own_data.md`) would close this gap.
3. **Rollover recall is not measurable.** No dataset has labelled
   rollovers. Its false-alarm rate *is* measured: 11 of 24,174 harsh
   events, and 0 on real roads.
4. **Real-road time is 4.7 hours**, recorded in Brazil and Bangladesh,
   not Pakistan.
5. **The score was fitted on 286 crashes.** It generalised well (81 % of
   4,221 unseen crashes), and fitting on more training files is a cheap
   improvement.
6. **VZCrash's sensors are not MPU-6050s.** They are the same class of
   sensor and the same range, but the thresholds should be re-checked
   with the real box (`own_data.md`).

## 4. Comparison with industry

| system | sensors | what it says it detects | published accuracy | relevance to us |
|---|---|---|---|---|
| **Apple Crash Detection** (iPhone 14+, Apple Watch, 2022) | high-g accelerometer up to **256 g**, high-dynamic-range gyroscope, GPS speed, barometer (airbag pressure), Bluetooth/CarPlay context | "**severe car crashes**": front, side, rear-end and rollover. Apple's support page says it **cannot detect all car crashes**. | none published. Publicised false calls from roller coasters and skiing. | Targets the same severe tier with a sensor of 16× the range and more inputs, and still states it misses some crashes and has false triggers. Our tiered target is the same claim, backed by numbers we publish. |
| **Google Pixel Car Crash Detection** | motion sensors, location, microphone | "**severe crashes rather than minor fender benders**". Google's example: being hit at ~40 km/h while stopped. Says it **may not detect all crashes**. | none published | Same target definition as ours. |
| **EU eCall** (mandatory in new EU cars since 2018) | the car's own crash sensors, e.g. **airbag deployment** | automatic call on a "**serious**" crash. The regulation's rationale: high-severity collisions where occupants may be incapacitated. | defined by airbag logic | The legal standard for automatic emergency calls in Europe is a severe-crash trigger, not "every contact". |
| **Airbag controllers** | accelerometers in the car body | deploy on **windowed velocity change (ΔV)** crossing a threshold; side-airbag deployment lower limit is about **3–5 g** lateral (SAE 07-12-02-0012) | proprietary | Our ΔV features are the same quantity, and our 4 g / 2.5 g rules sit in the same range. We use the airbag industry's own severity measure. |
| **Verizon's models on VZCrash** (the dataset's authors) | the same IMUs as our test data | crash vs non-crash on harsh events | best neural network (CNN-RNN, 1.7 M parameters): 97.5 % average precision in the lab, **~86 % on the live fleet stream**. At 75 % recall: their peak-g baseline gave 780 false positives among 735,000 events; the full CNN-RNN gave 10. | A large GPU-trained model still loses ~11 points in the field. Ours is 8 weights on a microcontroller, with physics guarantees for the severe tier. |
| **Smartphone threshold detectors** (Chalmers study) | phone accelerometer | crashes | ~**10 false alarms per hour** at 80 % sensitivity | That is the baseline a naive design hits. We measured 0 in 3 h. |

**What this means for the panel:**

- No production system claims to detect every crash. All of them define
  their target as severe crashes, and so do we.
- Commercial systems publish no accuracy numbers at all. This project
  publishes recall by severity tier, false-positive rates, false alarms
  per hour, the operating-point trade-off table, and the code to
  regenerate all of it.
- Our sensor is a ₨100 MPU-6050 at ±16 g. Apple's is 256 g. The physics
  overrides are what let a cheap sensor give a hard guarantee on the
  severe tier.
- The emergency-call flow (alarm → cancel window → automatic report with
  location) is the same pattern Apple and Google use.

## 5. v1 vs v2

### 5.1 What v1 was (and a correction)

The first engineer's work in this folder (`src/crash_detect.c`,
`bench/`, `results.md`, `info.md`) consisted of:

| part | state in v1 |
|---|---|
| **Peak g-force bands** (`gforce_band_update`), preset 5 / 20 / 40 g | written and benchmarked |
| **Tilt filter** (`tilt_filter_update`), complementary filter, rollover angle | written and benchmarked |
| **Acceleration jump + GPS speed drop** (`delta_speed_update`) | written and benchmarked; v1's own notes say the speed gate is wrong |
| **Weighted g + tilt score** ("Test 3b") | only as analysis in Python, with constants taken from the test data |
| **Moving-average "Layer 1"** (Pranoto et al.) | **designed in `info.md` but never implemented** — "Test 1 has not been run" |
| Decision rule, firmware, pothole logic, Jetson link | none |

The "moving average" method is therefore a **plan** from v1, not code. It
was designed to detect **emergency braking (near-misses)**, not crashes.
To compare fairly, we implemented it as the plan describes (moving
average of ‖A‖ over 0.58 s) and tested it as a crash detector too.

### 5.2 Same data through both: results

From `comparison.md` (generated by `eval/compare_v1.py`). Rows with `*`
re-run a v1 rule at the threshold that gives **the same harsh-event
false-positive rate as v2 (2.5 %)**, so they are compared at equal
false-alarm cost:

| rule | all crashes | severe | severe **missed** | harsh FPR | false alarms on 3 h real driving |
|---|---|---|---|---|---|
| v1-A: peak ≥ 5 G (the preset in v1's code) | 28.0 % | 46.2 % | **1,374** | 0.4 % | 0 |
| v1-B: peak ≥ 3 G (v1's recommendation) | 78.7 % | 99.9 % | 3 | 3.6 % | **4 (1.33 /h)** ✗ |
| v1-C: peak ≥ 3 G OR tilt ≥ 60° | 78.7 % | 99.9 % | 3 | 3.8 % | 4 (1.33 /h) ✗ |
| v1-D: Test 3b, tuned on test for 2 % FPR | 75.2 % | 98.6 % | 35 | 2.0 % | 1 |
| v1-B\*: peak ≥ 3.46 G | 67.9 % | 98.7 % | 33 | 2.5 % | 1 |
| v1-D\*: Test 3b at 3.58 | 80.1 % | 99.4 % | 15 | 2.5 % | 1 |
| v1-E\*: moving average (Layer 1, never built) | 75.2 % | 93.7 % | 162 | 2.5 % | 1 |
| v1-F\*: acceleration jump (Test 4) | 54.9 % | 80.2 % | 506 | 2.5 % | 5 |
| **v2 (this engine)** | **81.1 %** | **100.0 %** | **0** | 2.5 % | **0** |

How to read it:

- **v1 as shipped (v1-A)** would miss more than half of severe crashes:
  1,374 of 2,555. The only preset in its code is the textbook 5 G band,
  which v1's own benchmark showed doesn't work.
- **v1 as recommended (v1-B, 3 G)** catches severe crashes well, but
  produces **4 false alarms in 3 h of real driving (1.33 per hour)**,
  which **fails the ≤ 1/h target**. All four happen on **cobblestone at
  about 30 km/h**, with peaks of 3.2–3.5 g. A rule based only on peak g
  cannot tell a rough road from a crash. v2 sees the same jolts, but they
  are vertical, short and produce no velocity change, so it stays quiet.
- **At equal false-alarm cost**, v2 beats every v1 rule on overall recall
  and is the only one with **zero severe crashes missed** and **zero
  real-road false alarms**.
- **v1's best idea (Test 3b, v1-D\*) comes close** on overall recall
  (80.1 % vs 81.1 %), and is slightly better on moderate crashes. Be
  ready to say this honestly. It is still worse where it matters (15
  severe crashes missed vs 0; 1 real-road false alarm vs 0), and its
  constants were derived from the test data itself. In real use you
  would have to fix them in advance, which v1 never did. v2 keeps this
  idea: the tilt jump is one of its eight features.
- A note on the tier columns: the tiers are defined by peak g, so
  peak-threshold rules look perfect on whole tiers by construction (v1-B
  shows "100 %" moderate). Judge them by *all crashes*, *severe missed*
  and *real-road false alarms*.
- **The moving average (Layer 1)** is a poor crash detector (162 severe
  crashes missed at equal FPR). Averaging over 0.58 s smears a 50 ms
  crash pulse into the background. That was never its purpose: it was
  meant to detect braking. v2 does not need it, because near-misses are
  not alarm events.

### 5.3 What changed, and why

| v1 | v2 | why |
|---|---|---|
| Thresholds on **total** g (gravity and all directions mixed) | Reading split into **vertical** and **horizontal**, gravity removed, mount-angle independent | Potholes are vertical and crashes horizontal. Total g can't tell them apart: that is v1-B's 4 real-road false alarms. |
| Single-sample **peak** | Peak plus **50 ms sustained** horizontal and **ΔV over 100/300 ms** | A one-sample spike can be a glitch or a pothole edge. Sustained g and ΔV are what airbag controllers use. |
| Only preset: 5 / 20 / 40 G | Two **physics overrides** (2.5 g sustained horizontal; 4 g peak + 1.2 g horizontal) | Grounded in the tyre friction limit, not literature numbers that don't transfer to car IMUs. They guarantee the severe tier. |
| Test 3b score with **test-derived** z constants | **Logistic regression on 8 features**, fitted on **train**, threshold on held-out train | Deployable fixed constants and honest out-of-sample numbers. Keeps v1's useful tilt feature. |
| No sanity clamp (v1 known problem #3) | Clamp: > 20 g, > 2,500 °/s, stuck sensor | The data contains 50 g single-sample glitches. |
| GPS gate inside the detector, wrong shape (v1 known problem #1) | GPS speed **attached** to reports, **never a gate** | v1's own finding: speed drop can't separate crashes from near-misses. |
| Tilt ≥ 60° as a hard OR with peak g (made things worse in v1) | Rollover as its **own** branch, **held 1 s** | The hold removes the crash-impact fake tilt that made v1's OR fire falsely. |
| No pothole logic | Pothole / speed-bump branch, reported as a hazard | New requirement; feeds Feature 2. |
| 52 Hz design, 100 Hz data, conversions needed | **100 Hz** everywhere | Thresholds transfer directly; the MPU-6050 does it trivially. |
| Per-event peaks only (benchmark) | **Per-sample state machine**: capture → decide → alarm → countdown → confirm → lockout | This is what actually runs on a device. |
| No firmware, no link | ESP32 sketch, UART protocol, Jetson script, replay/demo tools | Needed for a working, integrable system. |
| Benchmark on VZCrash events only | Plus **3.0 h continuous real driving** and per-hour conversion | Your target is per hour, and the real-road test is what exposed v1-B's false alarms. |

**What v2 kept from v1:** the complementary tilt filter (unchanged, same
C function), the finding that the literature bands fail, the Test 3b
insight (tilt as a weighted feature), the decision to attach GPS rather
than gate on it, the C99 / float / no-heap coding rules, and the
benchmarking approach. v2 builds on v1's work rather than replacing it.

### 6.5 Step 4 — the live demo (optional, impressive)

Open **two** PowerShell windows in the same folder.

Window 1 plays the **Jetson**:

```
.venv\Scripts\python jetson\crash_link.py --tcp 9000 --gps-fake 40
```

Window 2 plays the **ESP32**, replaying a **real recorded crash** from
VZCrash in real time:

```
.venv\Scripts\python eval\replay.py vzcrash --label crash --n 0 --min-peak 4 --tcp 9000 --countdown 5
```

**What you'll see:** window 2 prints `CRASH` at the moment of impact.

sensor → detection → alarm → cancel window → report.

Then run window 2 again with `--label near_miss` instead of
`--label crash`. That replays a real **emergency stop**, and nothing
fires.
